## User-Requested Fastest-Completion Mode

Activate this mode only when the user explicitly asks to finish the computation as fast as possible, minimize wall time, maximize speed, or gives an equivalent instruction. It changes implementation strategy, not the requested result, evidence grade, correctness requirements, or completion gate.

1. Estimate whether the dominant work is safely decomposable and large enough to repay process, kernel-launch, data-transfer, synchronization, and memory overhead. Prefer a better algorithm, a vectorized or compiled implementation, or a backend's proven internal multithreading or accelerator path when it is likely faster. Do not blindly parallelize dependent, stateful, memory-bound, or very small work.
2. Inspect the selected execution environment's actual capacity: logical CPUs, accelerator count and memory (for example `nvidia-smi`, `torch.cuda.device_count()`, or `jax.devices()`), and, when an MCP tool is the selected primary backend, the capacity it reports while keeping the Mandatory Computation-Tool MCP Gate. For independent workloads, attempt an appropriate bounded parallel implementation such as a process pool, batched or vectorized execution, data-parallel training across the available devices, or concurrent independent grid cells, launching workers when needed and allowed. Give every worker the same code, configuration, dataset version, and seed policy.
3. When parallel overhead or worker capacity is uncertain and the full computation is expected to be long, compare serial and parallel execution on the same representative bounded slice selected under the call-window rules. Use the faster valid route for the full computation. Skip calibration for short jobs or when it would duplicate a material fraction of the requested work.
4. Treat failed worker or device launch, out-of-memory errors, license, quota, or server limits, unsafe decomposition, or a slower calibration as reasons to keep or return to the best serial implementation. State the limitation briefly; do not present the number of launched workers or devices as evidence of speedup.
5. Preserve exactness, precision, deterministic seeds where applicable, assumptions, and verification. Parallel reduction order, mixed precision, and nondeterministic accelerator kernels can change numerical results; state the declared tolerance when bitwise reproduction no longer holds. Run only the requested primary computation and proportionate checks; fastest-completion mode does not authorize redundant full-range runs.
