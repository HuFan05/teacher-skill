## Tool Call-Window and Long-Run Routing

Treat backend capability and transport suitability as separate questions. A backend can be callable and suitable for the task while a complete computation or training run is too long for one MCP or shell tool call.

1. Distinguish the backend's own limit (for example a solver `timeout` or a scheduler wall-time limit), an MCP execution tool's time limit, the outer MCP or host tool-call deadline, and the agent's process-monitoring window. A larger inner time limit does not extend an outer tool deadline. Discover documented limits when available; otherwise infer a conservative effective call window from bounded calls, never by sacrificing the full computation to a timeout.
2. Before a material full-range run, benchmark representative slices from the low, middle, and high-cost regions when cost varies with input size, sequence length, batch composition, configuration, or instance hardness. Include enough long sequences, large inputs, hard instances, and slow phases such as evaluation, checkpoint writing, JIT compilation, or data loading to reflect the dominant work. Do not extrapolate only from tiny, easy, low-end inputs or from warm-up steps. Compare serial and parallel routes on the same representative slice when parallelism may matter.
3. Put a safety margin between the conservative worst-case chunk estimate and every known inner or outer deadline. Normally target no more than one third of the shortest known call window, and never intentionally size a chunk above one half. Reduce the chunk further when runtime variance, startup or compilation cost, input-size skew, memory growth, or service load is uncertain.
4. Route by duration and recoverability:
   - use one tool call for work that comfortably fits the safety budget;
   - use bounded chunks, such as a fixed number of training steps, grid cells, or test shards, when each chunk fits, every completed chunk is checkpointed, and the final aggregation can prove complete non-overlapping coverage;
   - after the required capability or prototype check, including the actual MCP call when the route requires one, use an actually callable local executable or monitorable process for the full run when the calibrated workload cannot reasonably fit tool call windows. The capability check validates semantics and availability; it does not require using a tool call as the transport for an unsuitable long-running job.
5. The agent owns and reviews generated source code and configuration. Use MCP or short tool calls to confirm APIs, semantics, boundary cases, and representative outputs; do not rely on a single tool call as a durable source editor or background-process supervisor.
6. A long local run, such as a training job, must expose a process, job, or run identifier, compact progress or heartbeat (for example step, loss, and throughput), bounded resource use across host memory, accelerator memory, and disk, and atomic or otherwise validated checkpoints. A training checkpoint must include every state the resumed run needs: model, optimizer, learning-rate scheduler, data-loader or sampler position, and random-number-generator states. Prefer a yielded foreground process that the agent can resume waiting on; detach only when a durable monitor can unambiguously identify the process, progress, result, and failure state. Make resumed execution idempotent and prevent gaps, overlaps, or double counting of steps, samples, grid cells, or test cases.
7. Continue waiting while progress advances, resource use remains safe, and no correctness invariant fails, even when the original ETA was optimistic. Duration or ETA deviation alone is not a stopping condition. Diagnose a missing process, stagnant heartbeat, repeated errors, invalid checkpoints, non-finite loss where the run requires finite loss, or uncontrolled memory growth before deciding whether to resume, shrink chunks, or change route.
8. After any tool-call timeout or interrupted tool call, determine whether the backend evaluation or local process is still running before retrying, for example by inspecting the process table, the scheduler queue, the run's heartbeat or log file, or accelerator utilization. Do not launch a duplicate full-range computation while cancellation is uncertain; a duplicate training run can also contend for the same accelerator or overwrite checkpoints. Preserve and validate any completed checkpoints before recovery.
9. Preserve the requested evidence grade across the route change. A probabilistic filter may reduce exact-verifier work but cannot support an exact final claim by itself; retain every true candidate, handle equality and boundary exceptions explicitly, and send survivors to an exact or certificate-producing verifier, such as an SMT solver or model checker after random testing or fuzzing, when exactness requires it. Record every resume point of a resumed run; `exact_reproduction` of a resumed run requires the same restore states.
